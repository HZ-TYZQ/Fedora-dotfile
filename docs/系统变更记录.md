# Changelog

记录本机（Fedora 44 / niri 会话）系统配置的关键变更。

## 2026-08-22

### 用户配置迁移至 chezmoi

- **用户决定**：chezmoi 仅管理家目录中的用户配置，不接管 `/etc`、DNF、Snapper
  等系统级配置；整理和检查完成后由用户自行提交、推送 Git，并在确认归档内容后
  自行删除旧目录。
- **配置归属**：`~/.local/share/chezmoi` 成为用户配置的唯一长期来源；家目录是
  程序实际读取的部署结果。旧 `~/systemconfig` 中的 Niri、Noctalia 等副本不再
  作为配置来源。
- **文档迁移**：本变更记录迁入 chezmoi 的 `docs/系统变更记录.md`；chezmoi
  README 与操作指南补充唯一来源、排除范围和旧目录归档说明。
- **明确排除**：迁移备份、临时文件、VPN 配置与日志，以及 Snapper/DNF 系统脚本
  和测试不进入 dotfiles 仓库，随旧目录一并归档。
- **归档位置**：旧目录移动至 `~/Archives/systemconfig-legacy-20260822/`，保持普通
  目录形式，便于用户检查和按需恢复。

- **旧工作区归档**：`~/系统美化` 中的 GRUB 主题、预览图、实验变体和历史快照不

## 2026-08-14

### 修复 Dolphin 偶发黑白条纹配色

- **现象**：从 Noctalia 启动器直接打开 Dolphin 时深色配色正常，但经
  `xdg-desktop-portal` 或其他应用的“打开所在文件夹”启动时，文件列表偶发出现
  黑白交替行与深色背景上的黑色文字。
- **根因**：Niri `environment {}` 中的 `QT_QPA_PLATFORMTHEME=kde` 只传播给
  Niri 直接启动的进程，不会传播给 systemd、D-Bus 和 Portal 启动的进程；异常
  Dolphin 的进程环境确实缺少该变量，导致 KDE 深色方案与 Qt 默认调色板混用。
- **变更**：新增 `~/.config/environment.d/90-qt-kde.conf`，在 systemd 用户会话
  层统一设置 `QT_QPA_PLATFORMTHEME=kde`；同时删除 Niri `environment {}` 中的
  同值设置，避免维护两个来源。仓库 `config.kdl` 原本就未包含该变量，无需同步。
- **生效方式**：完整注销并重新登录后，Portal、D-Bus 服务及所有新启动的 Qt 6
  应用统一加载 Fedora 官方 `plasma-integration` 提供的 KDE 平台主题。

### 恢复 Dolphin 并补齐 XDG / KDE 默认应用

- **文件管理器**：Dolphin 已重新安装并设为 `inode/directory` 的 XDG 默认处理器；
  Nemo 暂时保留作为回退，不再是目录默认应用。
- **Dolphin 打开文件**：视频 MIME 类型继续指向系统级 Flatpak Haruna
  (`org.kde.haruna.desktop`)；Markdown 的默认应用与 Added Association 均从
  Apostrophe 改为 Neovim (`nvim.desktop`)。Apostrophe 本体仍保留，可在“打开方式”
  中手动选择。
- **Dolphin 打开终端**：KDE 的 `TerminalApplication` / `TerminalService` 改为
  `kitty` / `kitty.desktop`，与 `xdg-terminal-exec` 的 Kitty 首选项保持一致。
- **验证**：`kbuildsycoca6 --noincremental` 已刷新 KDE 应用缓存；XDG 查询确认十种
  已配置的视频 MIME 类型均使用 Haruna、Markdown 使用 Neovim；KDE 与 XDG 的终端
  读取值均为 Kitty。Haruna Flatpak 1.8.1 的桌面入口及 MIME 注册有效。

### 音频默认应用：Tauon → Haruna

- **现象**：Dolphin 用系统级 Flatpak Tauon 11.1.1 打开 FLAC 时没有播放文件；随后
  手动误选 Neovim 打开约 95 MiB 的 FLAC，使 `copilot.lua` 的 Node.js language
  server 耗尽 V8 堆内存并崩溃。Node.js 与 Copilot 插件本身不是文件打开失败的根因。
- **根因**：Tauon 导出的桌面入口将文件路径传给
  `com.github.taiko2k.tauonmb.sh`，但该脚本当前只接受 `playpause`、`next` 等遥控命令，
  因而把 FLAC 路径报为 `Invalid command`。文件 MIME、Dolphin 调用、Flatpak
  `xdg-music` 权限及文件可读性均正常。
- **用户决定**：不创建需要后续维护的 Tauon 用户级桌面入口覆盖，直接采用 Haruna
  回退；Tauon 保留安装并继续出现在“打开方式”候选中。
- **变更**：将 Haruna Flatpak 桌面入口声明支持的十种音频 MIME（AAC、AC3、FLAC、
  MP4 Audio、MPEG Audio、Ogg、WAV、WebM Audio、Matroska Audio、MPEG URL）设为
  `org.kde.haruna.desktop`，并刷新 KDE 应用缓存。未修改其他默认关联。
- **验证**：十种音频 MIME 的 XDG 查询全部返回 Haruna；目录仍由 Dolphin 打开，
  Markdown/纯文本仍由 Neovim 打开，视频仍由 Haruna 打开，Dolphin 终端仍为 Kitty。

### 修复 Neovim Markdown 中文内容满屏红色波浪线

- **现象**：Neovim 打开 Markdown 时大段中文被划红色波浪线；光标处
  `vim.diagnostic.open_float()` 提示无诊断，排除 lint/LSP 来源。
- **根因**：LazyVim 内置自动命令 `lazyvim_wrap_spell` 会给 markdown 等文本类型
  开启 `spell` 拼写检查；词库为英文（`spelllang=en`），中文全部命中 `SpellBad`
  高亮，在 vscode 主题下为 `#f44747` 红色 undercurl。该自动命令在 VeryLazy
  （有 UI）后才注册，headless 排查时表现为 `spell=false`，一度误判为
  markdownlint 诊断（已一并关闭，见下）。
- **变更**：`~/.config/nvim/lua/config/autocmds.lua` 删除
  `lazyvim_wrap_spell` 组，并以自定义 `wrap_no_spell` 自动命令保留原有的
  自动换行行为、仅关闭拼写检查；新建
  `~/.config/nvim/lua/plugins/markdown.lua`，将 nvim-lint 的
  `linters_by_ft.markdown` 清空（用户选择完全禁用 Markdown lint）。
- **未变更范围**：marksman LSP、render-markdown 渲染美化、markdown-preview
  预览等功能不受影响；链接上的直线下划线是主题对 `@markup.link` 的正常样式。
- **验证**：headless 中手动触发 `User VeryLazy` 模拟真实会话，改前打开
  Markdown 为 `SPELL=true`，改后为 `SPELL=false` 且 `WRAP=true`；含尾随空格与
  长中文段落的测试文档诊断数为 0。
- **后续可选**：如需保留英文拼写检查但跳过中文，可在 options 中设置
  `vim.opt.spelllang = { "en", "cjk" }`。

### 修复 Noctalia 启动终端程序时使用 Ghostty 而非 Kitty

- **现象**：从 Noctalia 启动器打开 Neovim（`nvim.desktop`）、music-player
  （`music-player.desktop`）等 `Terminal=true` 的程序时，拉起的是 Ghostty
  而非 Kitty。
- **根因**：Noctalia 5.0 启动 `Terminal=true` 程序时自行选择终端，不经过
  系统默认终端配置（Niri 绑定、xdg-terminal-exec、KDE/GNOME 默认值均已是
  Kitty）。其逻辑为先读 `$TERMINAL` 环境变量（当时未设置），未设置则按
  内置顺序 `gnome-terminal → ptyxis → x-terminal-emulator → ghostty →
  kitty → ...` 选取第一个已安装的终端；Ghostty 仍安装且排在 Kitty 之前，
  故被选中。该顺序提取自 Noctalia 二进制字符串表，与实际观察到的行为一致。
- **变更**：新建 `~/.config/environment.d/50-terminal.conf` 设置
  `TERMINAL=kitty`，沿用 `90-qt-kde.conf` 的 environment.d 机制，经 systemd
  用户会话传播给 Niri 及 Noctalia；仓库 `config.kdl` 不含该变量，无需同步。
- **生效方式**：由用户自行注销并重新登录，未立即修改当前会话环境或重启
  Noctalia。
- **未变更范围**：Ghostty 程序与 `~/.config/ghostty` 配置保留，未卸载或
  删除。
- **验证**：environment.d 生成器解析确认输出 `TERMINAL=kitty`；重登录后
  Noctalia 启动 Neovim / music-player 的实际终端待用户确认。

### 修复：应用无法唤起文件管理器（"打开文件夹"无反应）

- **现象**：任意应用请求"打开文件夹"时无反应或行为异常。
- **根因**：`inode/directory` 的默认应用从未显式设置，系统全局配置指向未安装的
  Nautilus；回退逻辑按字母序选中了 kitty 附带的 `kitty-open.desktop`
  （kitty 0.47.1 于当日更新引入），其 `kitty +open %U` 并不会打开文件管理器。
- **变更**：`xdg-mime default org.kde.dolphin.desktop inode/directory`
  → 写入 `~/.config/mimeapps.list`。

### 修复：QQ / OBS 等应用的文件对话框完全无反应

- **现象**：QQ 聊天"文件"按钮、OBS 更改录像储存路径的"浏览"按钮点击后无反应
  （KDE Plasma 会话中正常）。
- **根因**：niri 会话的 portal 默认后端为 gnome，而 xdg-desktop-portal-gnome 50 起
  将 FileChooser 委托给 `org.gnome.Nautilus`（本机未安装），D-Bus 激活失败
  （日志：`Delegated FileChooser call failed: The name is not activatable`）。
- **变更**：新建 `~/.config/xdg-desktop-portal/niri-portals.conf`，在系统
  niri-portals.conf 基础上增加 `org.freedesktop.impl.portal.FileChooser=kde;`，
  将文件选择对话框路由到已安装的 xdg-desktop-portal-kde 后端
  （删除该文件可恢复系统默认）。已 `systemctl --user restart xdg-desktop-portal`。
- **验证**：portal FileChooser 调用可弹出 KDE 文件对话框；
  `org.freedesktop.FileManager1`（"在文件夹中显示"）激活 Dolphin 正常。

### 修复：QQ 无法使用 Fcitx5 输入法

- **现象**：QQ（Electron，经 XWayland 运行）里输入法完全无响应。
- **根因**：会话从未设置输入法环境变量（`XMODIFIERS`/`GTK_IM_MODULE`/
  `QT_IM_MODULE`）。X11 应用只靠 XIM 协议使用 fcitx5，而 XIM 必须由
  `XMODIFIERS=@im=fcitx` 指向才会启用；KDE 下是 Plasma 自动设置这些变量，
  迁到 niri 后无人设置。（fcitx5 本身正常，XIM 服务已在 :0 注册。）
- **变更**：niri 配置（`~/.config/niri/config.kdl` 与仓库 `config.kdl` 同步）
  顶部新增 `environment {}` 块：`GTK_IM_MODULE`/`QT_IM_MODULE`/`SDL_IM_MODULE`
  设为 `fcitx`，`XMODIFIERS` 设为 `@im=fcitx`；已通过 `niri validate` 校验。
  当前会话用 `systemctl --user set-environment` + `dbus-update-activation-environment`
  立即补齐（对 systemd/D-Bus 激活的应用生效）；从启动器打开的应用需**重新登录**后生效。

## 2026-08-15

### 屏蔽桌面用户对 /dev/udmabuf 的访问（phonto CPU 占用修复）

- **原因**：phonto（视频壁纸）播放 4K 视频时宿主机 CPU 占用 20–24%（dev 容器内同
  二进制仅约 7%）。完整排查记录见
  `~/Projects/phonto-main/analyze.md`（附 3）。根因链：宿主机 udmabuf 可用 →
  GStreamer glupload 的 udmabuf uploader 在 allocation query 中抢占 pool[0] →
  nvh264dec（GstVideoDecoder 基类只认 pool[0]）无法用该 dmabuf pool 重配 →
  回退系统内存输出 → glupload 退化为 Raw Data 逐帧 CPU 上传（4K30 NV12 约
  745MB/s）。容器内因权限被拒反而选中 GLBufferPool/GLMemoryPBO 的 GPU 路径。
- **改动**：`sudo chmod 000 /dev/udmabuf`。未添加 udev 规则，设备节点的 uaccess
  ACL/seat 标签仍在，仅 mode 归零使全部用户态访问被拒。
- **效果（实测）**：phonto CPU 由 20–24% 降至 7.3%（单核），显存 358→418MiB
  （GL bufferpool 的代价），两项特征值与容器侧 GL PBO 路径完全一致。
- **影响面（实测评估）**：本机仅 chrome、protonvpn 在初始化探测时持有旧 fd，
  均有 shm/memfd 回退，重启后无感；niri/NVIDIA 驱动/PipeWire 不使用该设备；
  QEMU 仅装了二进制（无 libvirt/virt-manager），未在使用。将来若跑
  virtio-gpu GL 加速虚拟机，需恢复权限。
- **已知限制**：chmod 在重启或 `udevadm trigger` 后会被 udev 恢复为默认权限，
  **非持久化**；如需长期生效，需后续添加 udev 规则（如
  `KERNEL=="udmabuf", TAG-="uaccess"` + mode 限制）。
- **回滚**：`sudo chmod 660 /dev/udmabuf`，或 `udevadm trigger --name-match=udmabuf`
  恢复 udev 默认。

## 2026-08-16 00:00

### `/dev/udmabuf` 持久限制规则修正（前两版失效记录与终版）

- **背景**：昨日 23:33 的 `99-disable-udmabuf.rules` 重启后失效。规则只设置了
  `OWNER/GROUP/MODE`，未摘除 uaccess 标签：`70-uaccess.rules`（Fedora 自带，
  第 38 行）对 udmabuf 执行 `TAG+="uaccess"`，`73-seat-late.rules` 在登录时由
  systemd-logind 据此注入 `u:tyzq:rw-` ACL，普通用户仍可打开设备，phonto 回到
  慢路径（实测 CPU 23.7%，显存 358MiB）。
- **第二版失败**：改为 `60-disable-udmabuf.rules` 并加入 `TAG-="uaccess"`，但
  排序早于 `70-uaccess.rules`：先摘一个尚不存在的标签，随后 70 再加回，仍被
  注入 ACL。
- **终版**：`/etc/udev/rules.d/71-disable-udmabuf.rules`
  `KERNEL=="udmabuf", TAG-="uaccess", OWNER:="root", GROUP:="root", MODE:="0600"`
  ——排在 70-uaccess 之后、73-seat-late 之前，摘标签后 logind 不再注入 ACL。
  删除了旧的两版规则文件。
- **当前会话收尾**：`udevadm trigger --name-match=udmabuf` 重放规则链
  （`CURRENT_TAGS` 已无 uaccess）+ `setfacl -x u:tyzq /dev/udmabuf` 清除本会话
  存量 ACL，重启 phonto 生效。
- **验证（实测）**：tyzq 打开 `/dev/udmabuf` 权限拒绝；phonto CPU 6.8%（15s
  采样，单核），显存 418MiB——两项均为 GL PBO 快路径特征值，与容器侧一致。
- **经验**：udev 规则的 `TAG-=` 必须排在对应 `TAG+=` 规则之后执行；文件名前缀
  编号即执行顺序，只改 mode 挡不住 uaccess/ACL 注入路径。
- **回滚**：删除该规则文件并 `udevadm trigger --name-match=udmabuf`，下次登录
  恢复 udev 默认（root:kvm 660 + uaccess ACL）。
